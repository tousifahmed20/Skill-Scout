# Decisions log (for humans)

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-10-11 | Pull, not push: a skill answered on demand, no newsletter | Answers at the moment of need; no email infrastructure; no "no updates today" problem |
| D2 | 2026-10-11 | Scope = agent skills only | Owner's call. Keeps one clear job: find the best agent skill. MCP servers, subagent definitions, and config packs are out. |
| D3 | 2026-10-11 | Users' own models do evaluation; results go to a shared Hive | Removes our per-query LLM cost; each evaluation is paid once and reused |
| D4 | 2026-10-11 | ICM folder layout with routed reads (Jake Van Clief's Interpretable Context Methodology) | Each feature loads only its own stage plus named sections of earlier stages. Less context, fewer mistakes, and routes are checked by a script. |
| D5 | 2026-10-11 | Stage contracts are named `CONTEXT.md`, not nested `CLAUDE.md` | Claude Code auto-loads a subfolder's `CLAUDE.md` whenever it reads a file there. Cross-stage reads would pull in unrelated contracts. `CONTEXT.md` loads only when routed. |
| D6 | 2026-10-11 | No `@path` imports in routing files | Claude Code loads imports at launch, which would load everything and defeat routing |
| D7 | 2026-10-11 | Compatibility is a filter and a display, not a quality score | Whether a skill runs in your harness is a yes/no for you; it says nothing about how good the skill is |
| D8 | 2026-10-11 | Task-fit gate before scoring | A high-quality skill that doesn't do your task should never be #1. Fit is judged from evidence fields, not descriptions. |
| D9 | 2026-10-11 | Membership checks only "is this a real skill" | Quality, popularity, and maintenance belong to later stages. Spec deviations are warnings, not rejections, so working skills aren't wrongly excluded. |
| D10 | 2026-10-11 | Injection = content that targets the evaluator, ranker, or host | A SKILL.md is instructions by design. Flagging every instruction would exclude every skill. |
| D11 | 2026-10-11 | One implementation for client and server scripts (`rank.py`, `fetch_evidence.py`) | Two copies drift; drift would make cached and fresh results disagree |
| D12 | 2026-10-11 | New skills get reserved shortlist seats | They have no health history, so a health-based shortlist would bury them before evaluation |
| D13 | 2026-10-11 | The shipped skill uses spec frontmatter only | Our own skill must be compatible across harnesses, like the skills we recommend |
| D14 | 2026-10-11 | Stack lives in `CLAUDE.md`, not a separate file | Every coding stage needs it, and `CLAUDE.md` is always loaded; a separate file would add a read to every route |
| D15 | 2026-10-11 | Shipped skill scripts use the Python standard library only | Users should not have to install packages to run the skill in any harness |
| D16 | 2026-10-11 | ~~One database (Postgres + pgvector) for dev and hosted~~ — superseded by D17 | — |
| D17 | 2026-10-11 | v1 is free: no server, no recurring charges. GitHub Actions builds a SQLite index; GitHub Releases hosts it; stages 10–11 move to v2 | Owner's call: free first batch, $5 one-time seeding at most. A free database tier would still risk limits or pausing; a release file has neither. |
| D18 | 2026-10-11 | The skill retrieves by text search (SQLite FTS5 / BM25) using search terms the user's model writes; embeddings run only in GitHub Actions | Embedding the query on the user's machine would need extra packages; model-written synonyms keep recall high with the standard library |
| D19 | 2026-10-11 | No spot checks or audits in v1 | They exist to audit results users share with each other; v1 shares nothing. A changed skill is simply re-evaluated by the next user's own model. |
| D20 | 2026-10-11 | New skills are evaluated in users' sessions, not by the owner | Keeps v1 at $0 per month; reserved shortlist seats make sure new skills still get evaluated |
| D21 | 2026-10-11 | Seed evaluations are committed to the repo as JSON files and imported on every build | The scheduled build starts on a blank runner; anything not in the repo would be lost. Committed files are also reviewable and versioned. |
| D22 | 2026-10-11 | User-side GitHub calls use the user's own access: GitHub CLI login, Git's saved login (with consent), or a free read-only token in `~/.skill-scout/config.json`; anonymous as a last resort | Owner's call. The owner's quota must never depend on user count. Harnesses don't expose their GitHub connections to scripts, but most rely on the GitHub CLI or Git's login, so reusing those is the closest to "their GitHub login". |
| D23 | 2026-10-12 | Embedding model = `sentence-transformers/all-MiniLM-L6-v2` (384-dim, CPU), run only in the GitHub Actions build (stage 05, recorded in `embed.py`) | CLAUDE.md asks stage 05 to pin the exact model. Small, CPU-friendly, and widely used for semantic similarity; the shipped skill never embeds (it searches text), so this dependency lives only in CI. Change here, not in code. |
| D24 | 2026-10-12 | "Established account" is decided only from `created_at` + `public_repos`; no GitHub user-id age proxy | A monotonic user-id threshold can't be verified and drifts over time; a wrong constant silently mislabels real accounts. Signals that lack `created_at` (stargazer/fork samples) degrade to "unknown" (null) rather than guess, and ranking redistributes their weight. |
| D25 | 2026-10-12 | Skill renamed `agent-finder` → `skill-scout` (display "Skill Scout") across the whole product namespace: skill dir, `name:`, user cache `~/.skill-scout/`, env `SKILL_SCOUT_*`, release asset, install command, prose | "Agent Finder" named the wrong noun — the skill finds *skills*, not agents — and "Meta Agent Finder" also collided with the Meta brand. A full rebrand (not a half-rename) avoids a mixed namespace (`skill-scout` skill reading `~/.agent-finder/`). The on-disk dev workspace folder stays `agent-finder`; the repo name is the owner's call at going-live. |
